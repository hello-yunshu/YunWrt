# D3 · 版本跟随上游最新，不锁点版本

- 状态：已采纳
- 日期：2026-11-12
- 关联：[迁移方案 §0.1、§0.3、§6 D3](../plans/2026-11-11-yunwrt-migration.md)

## 背景

前三版方案的做法是把设备那一刻的状态钉死：锁 OpenWrt 点版本、锁 feed 哈希、要求包清单逐次一致。这与 YAOF 的滚动更新方式正面冲突——上游本身就是每天重建，钉死等于把一个滚动项目手动改成静态项目，维护成本持续累积，收益只是"看起来稳定"。

## 决策

**完全不锁版本。** 版本由 YAOF 分支和上游 `scripts/build.sh` 的 `resolve_version()` 决定，上游升到 25.13 也照走。

具体禁止：

- 仓库内不得出现 OpenWrt 点版本常量（`OPENWRT_SERIES`、`OPENWRT_VERSION` 之类的 `env` 文件或变量）；
- 不得出现版本策略枚举、点版本白名单、`upstream.lock`；
- 构建入口不向 `build.sh` 传版本参数；
- 不得以"记录里的版本变了"为由让构建失败。

允许记录：`build-log/` 可以写实际解析出的 `openwrt_version`、`kernel_version`、`vermagic`，它们只是排障线索，不参与任何校验或回退。

## 理由

1. 整包出镜像时包与内核同源，vermagic 只对"向运行中的设备单独安装 kmod"构成约束，本项目不做这件事。
2. 真正的故障源不是版本漂移，而是 overlay/patch 在上游文件变形后静默失效（[D9](D9-base-drift-hard-fail.md) 用 base 校验解决）。
3. 钉死会让人误以为"构建成功"等于"交付成功"，从而掩盖失效。

## 后果

- 每次上游变更都要跑能力验收，这是唯一的兜底。
- 想改回锁定，必须重新走一次决策评审，并同步删除本 ADR 与 §0.3 的反向约束。
